# ADR-0001: バックエンドを同期実装とし、ジョブキューを採用しない

- **ステータス**: 採用
- **決定日**: 2026-08-09
- **対象範囲**: `backend/`
- **決定者**: 初期実装時

---

## 背景

承認ワークフロー SaaS の初期実装にあたり、バックエンドの実行モデルとして次の3案があった。

| 案 | 構成 |
|---|---|
| **A** | 同期実装 + ジョブキューなし |
| **B** | 同期実装 + ジョブキュー（Celery / arq / RQ） |
| **C** | 全面 async（`AsyncSession` + asyncpg/aiosqlite）+ ジョブキュー |

判断材料となる要件は以下だった。

- 「ローカルで動く状態」を成果物とする（起動手順を増やしたくない）
- 承認・却下・差戻しといった状態遷移が処理の中心で、いずれも短時間で完結する
- 監査ログと通知は状態遷移と**必ず一緒に**記録されなければならない（決裁システムとしての要件）
- 初期の永続化層は SQLite

## 決定

**案 A を採用した。**

具体的な実装は次のとおり。

- FastAPI のエンドポイントはすべて同期関数（`def`）で定義する。`async def` はライフスパンと例外ハンドラのみ（フレームワークの要求）
- SQLAlchemy は同期エンジン・同期 `Session` を使う
- 通知（`Notification`）は `workflow_service._notify()` が状態遷移と**同一トランザクション内**で INSERT する
- ジョブキュー、ワーカープロセス、`BackgroundTasks`、スケジューラはいずれも導入しない
- 通知のクライアントへの反映は、フロントエンドの 30 秒ポーリングで行う

## 理由

### 1. 処理が I/O 律速ではない

承認1回の処理は「数クエリ + 数 INSERT」で完結する。外部 API 呼び出しや長時間の待機がないため、非同期化しても待ち時間は縮まない。非同期化が効くのは待ちが支配的な処理であり、本システムはそれに当たらない。

### 2. 中途半端な async はむしろ有害

`async def` エンドポイントから同期 SQLAlchemy を呼ぶと、DB アクセス中にイベントループを塞ぐ。これは同期実装より悪い。正しく async 化するには `AsyncSession` + 非同期ドライバまで一式揃える必要があり、テスト97件もすべて async に書き換えることになる。

一方、FastAPI は `def` で定義されたエンドポイントを自動的にスレッドプールへ逃がす。同期 I/O を使う限り、これが本来想定された使い方である。

### 3. SQLite が書き込みを直列化する

永続化層が書き込みを直列化するため、アプリケーション側を非同期化しても書き込みスループットは改善しない。ボトルネックの位置が違う。

### 4. 運用部品を増やさない

ジョブキューの導入は Redis（またはブローカー）とワーカープロセスを要求する。起動手順が 2 プロセス（API + フロントエンド）から 4 プロセスに増え、「ローカルで動く」という要件と直接ぶつかる。

### 5. トランザクション整合性が素直に得られる

現在の設計では、状態遷移・監査ログ・通知が同一トランザクションでコミットされる。そのため **「承認は通ったのに通知が発行されていない」という不整合が構造的に発生しない**。決裁システムにおいてこの性質は重要であり、初期段階でこれを無償で得られることの価値は高い。

## 結果

### 得られたもの

- 通知の欠落・監査ログの欠落が構造的に起きない
- テストを同期で書けるため、テストコードが読みやすく速い（pytest 97件が約6秒）
- 起動が API + フロントエンドの 2 プロセスで完結する
- 障害時の調査対象が単純（キューの滞留やワーカーの死活を考えなくてよい）

### 失ったもの・制約

- **外部システムへの通知（メール・Slack 等）を現在の設計のまま追加できない**（後述）
- **承認の滞留を検知する仕組みがない**。SLA 超過や督促といった、稟議システムとして本来必要な機能を持てない
- リクエスト内で完結しない長時間処理（大量エクスポート等）を受けられない
- 水平スケールはプロセス数を増やす方法に限られる

## 再検討のトリガー

以下のいずれかに着手する時点で、この決定は見直す必要がある。

1. **外部システムへの通知（メール・Slack・Teams）を実装するとき** — 必須。理由は次節
2. 承認の督促・SLA 超過エスカレーションを実装するとき（定期実行が必要）
3. レポート生成・CSV エクスポートで 1 リクエストが数秒を超えるようになったとき
4. PostgreSQL 移行後、書き込みの同時実行がボトルネックとして観測されたとき

### なぜ外部通知の追加が必ずトリガーになるのか

外部送信を現在の `_notify()` の位置（＝トランザクション内）で同期的に行うと、二重書き込み問題が発生する。

- 送信は成功したが、その後トランザクションがロールバックされる → **実体のない通知が届く**
- 送信が失敗して例外が飛ぶ → **承認処理そのものが失敗する**

どちらも決裁システムとして許容できない。したがって外部通知の追加時には、非同期実行の仕組みが構造上必要になる。

## 実装するときの指針

将来ジョブを導入する際の方針を、判断の前提とあわせて残しておく。

### 継ぎ目は 1 箇所

`Notification` を生成しているコードは `backend/app/services/workflow_service.py` の `_notify()` **1 箇所だけ**である（他のモジュールを含め、モデルのコンストラクタを呼ぶ場所は他にない）。ここを outbox テーブルへの INSERT に差し替えれば、状態遷移との同一トランザクション性を保ったまま、実際の送信をワーカーへ委譲できる（transactional outbox パターン）。既存の `Notification` テーブルを outbox 兼用に拡張する案と、別テーブルを設ける案の双方が取れる。

`_notify()` の呼び出し元は公開関数（`approve` / `reject` / `send_back` / `add_comment`）と内部ヘルパ（`_activate_current_step` / `_notify_approvers`）の計 8 箇所だが、**いずれも変更する必要はない**。

### 導入順序

1. **outbox + ワーカー** — 外部通知。整合性の要求が最も強く、設計上の影響も最大
2. **定期ジョブ** — 督促・SLA 超過エスカレーション。1 の基盤に相乗りできる
3. **非同期ワーカーでの重い処理** — エクスポート・一括更新

### async への全面移行は最後で良い

上記 1〜3 はいずれもジョブ実行基盤の話であり、リクエストハンドラの async 化とは独立している。ハンドラの async 化は単体では効果が薄いため、優先度は最も低い。実施するなら PostgreSQL + asyncpg への移行と同時に行う。

## この決定に含まれない関連課題

本決定の検討中に見つかったが、非同期化やジョブとは別の問題として切り分けたもの。

- **`GET /api/v1/analytics/summary` がテナントの全申請行を Python 側にロードして集計している**（`app/api/routers/analytics.py` の `_scope_select`）。SQLite / PostgreSQL 双方で動く可搬性を優先した結果だが、管理者が大規模テナントで実行すると素直に重い。**正しい対処は SQL の集計クエリへの書き換えであり、ジョブ化ではない。** ジョブ導入を検討する前にこちらを解消すべきである
